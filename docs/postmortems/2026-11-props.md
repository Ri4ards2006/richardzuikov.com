# Postmortem: 3D Descent Props Drift & Lifecycle Failures

**Date:** 2026-11-10  
**Authors:** Claude Code (Implementer), Antigravity (QA / Systems Architect)  
**Status:** Resolved (Merged in `feat/atlus-v7`)  
**Impact:** High visual degradation on desktop; missing props during descent; drift accumulated across scroll bursts.

---

## 1. Executive Summary
During the development and testing of `feat/atlus-v6`, two critical issues severely impacted the 3D descent props system:
1. **Incident 1 (Drift Bug)**: 3D meshes visibly drifted up to 45–90 px away from their designated manga panel gutter slots during rapid, reciprocal wheel scrubbing.
2. **Incident 2 (Disappearing Props Bug)**: Panel 02 (the microchip) and Panel 05 (the security camera) vanished at multiple scroll positions, and the dome camera was erroneously claimed or culled after navigating into `/about`.

Both issues were resolved through a fundamental transition from spring-based mutable physics to deterministic stateless projection, backed by pixel-probe automated regression testing.

---

## 2. Incident 1: The Drift Bug

### Timeline & Symptoms
- On `feat/atlus-v4` and `v5`, 3D props were coupled to manga panels using interactive spring physics (`target` tracking with damping coefficients).
- When a user scrubbed down the page and quickly reversed back to the top, props failed to return to their rest positions, accumulating residual positional error (`|Δ| > 15px`).
- In extreme cases (5× rapid scroll bursts), the microchip and camera hovered directly over editorial text.

### Root Cause Analysis (5 Whys)
1. **Why did the props drift?**  
   The anchor calculation used `getBoundingClientRect()` inside an active animation frame while Lenis virtual scroll transformations were mid-flight.
2. **Why did `getBoundingClientRect()` return divergent values?**  
   On a page utilizing smooth-scroll momentum, `getBoundingClientRect()` reflects the current visual position of the layout box *before* the current frame's scroll transform has completed layout reflow. Reading `getBoundingClientRect()` relative to `offsetParent` introduced a cumulative phase offset.
3. **Why did the springs exacerbate the drift?**  
   The spring integrator maintained mutable internal velocities (`vx`, `vy`) and delta-time accumulators. Uneven RAF intervals during heavy GPU frames caused numerical integration drift.
4. **Why did the initial E2E test suite miss it?**  
   The early drift test in `test/e2e-v6` queried `[data-prop]` DOM elements via `page.locator().boundingBox()`. Because the DOM proxy updater applied the exact same drifted position calculated by Three.js (`node.style.transform = ...`), the DOM proxy and the WebGL mesh agreed with each other perfectly—even though both were in the completely wrong place!

### Resolution
- Replaced spring physics with a **pure stateless projection function**:
  $$\text{PropPos} = f(\text{ScrollY}, \text{CameraMatrix}, \text{PanelStaticLayout})$$
- Eliminated all mutable velocity accumulators in `descent-props.js`.
- Authored `window.__propScreenPos()`, projecting the actual WebGL mesh geometry through the camera projection matrix onto viewport pixels (`getWorldPosition().project(camera)`), proving zero drift (`|Δ| ≤ 1px`).

## 3. Incident 2: Disappearing Props Post-v6

### Timeline & Symptoms
- In `feat/atlus-v6`, while drift was mitigated, Panel 02 (the microchip) and Panel 05 (the dome camera) disappeared entirely when scrolled into view.
- Visiting `/about` and returning to `/` caused the dome camera to detach or become permanently invisible.

### Root Cause Analysis
1. **Over-Aggressive Collision Culling**:  
   In `v6`, a collision avoidance sweep was added:
   ```javascript
   const parallax = [panel.parallax, ...PARALLAX_CANDIDATES].find((candidate) => !collides(candidate));
   if (parallax === undefined) return; // anchor became null!
   ```
   If any parallax candidate intersected a neighboring panel's theoretical depth envelope, `item.anchor` was set to `null`, which immediately forced `item.root.visible = false`. The culling radius was set too conservatively, dropping valid props in standard 1440×900 desktop layouts.
2. **Scene Hierarchy Theft via Sub-Screens**:  
   When navigating to `/about`, the page mounted `<PropViewer name="domeCamera" />`. Because the 3D mesh asset was loaded as a shared Three.js Object3D instance, re-parenting it to the `/about` inspection scene detached it from the primary `stage` descent scene. When returning to `/`, the mesh remained detached or had its world matrix invalidated.
3. **Frustum Culling Disconnect**:  
   `CULL_DISTANCE = 9` (world units) culled props near the viewport edges before they exited screen view.

### Resolution
- Rewrote the collision solver with relaxed tolerance margins and fallback anchor clamping so `item.anchor` is never discarded when a panel is centered in the viewport.
- Cloned mesh geometries for modal viewers (`PropViewer`), ensuring sub-screens never borrow or re-parent live descent scene objects.
- Added explicit frustum intersection checks (`frustum.intersectsObject(mesh)`) and scene hierarchy contracts (`scene.name = 'descent'`).

## 4. Blameless Lessons Learned

1. **Test the Pixels, Not the Proxies**:  
   Never verify WebGL behavior solely through DOM proxies or synthetic mirrors. The only definitive proof of rendering is the **Pixel Probe** (CIELAB ΔE difference against background `#050505` on canvas screenshots).
2. **Stateless is King in Declarative UI**:  
   In reactive applications with virtual scroll (Lenis, GSAP ScrollTrigger), mutable physics state (springs, velocities) will always drift under rapid direction changes. Derive all spatial coordinates directly from the scroll progress variable.
3. **Asset Isolation Across Routes**:  
   Shared 3D meshes cannot be multi-parented in Three.js. Standalone modal viewers must instantiate their own clones or procedural instances to prevent lifecycle leaks across page routes.
